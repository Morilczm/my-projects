# 更新与恢复

## 三种更新各走一条路径

| 改动 | 操作 | 是否仅推送主站 GitHub 就生效 |
| --- | --- | --- |
| 主站代码、页面样式 | 修改主站仓库，推送到 Cloudflare 已连接的部署分支，确认构建与部署成功；或手动 `pnpm run build`、`pnpm exec wrangler deploy`。 | 已正确配置自动部署时可以。 |
| PDF、ZIP、JPG、WEBP | 上传到 `byrdocs-file`，key 为文件名；必要时在 Archive 添加对应元信息。 | 不可以。 |
| 标题、分类、课程等资料元信息 | 修改 Archive `metadata/*.yml`，重新生成 `metadata.json`，上传到 `byrdocs-data`。 | 不可以；Archive 的 R2 Actions 尚未改造。 |

若增加或修改数据库结构，还要按项目迁移流程对目标 D1 执行新的迁移。更换 Worker 域名时，应重新生成 `metadata.json` 和三个 YAML 的站点 URL/校验规则，并调整相应构建变量。

## 手动重建数据文件

先将 `source/byrdocs-archive-25df779.zip` 解压为 Archive 目录，或使用原位置 `E:\byrdocs-archive`。资料原件需从原电脑的 `E:\byrdocs-reproduction\resources` 取得，GitHub 不含这些大文件。在拥有 PyYAML 的 Python 环境运行 `tools/build_byrdocs_data.py`；参数示例见 [复现过程](复现过程.md)。生成结果先检查记录数量、链接域名和缺原件数，再上传：

```powershell
$ossutil = 'E:\oss-tools\ossutil-2.1.2-windows-amd64\ossutil.exe'
$dataDir = 'E:\byrdocs-reproduction\data\regenerated'
foreach ($name in @('metadata.json','book.yaml','test.yaml','doc.yaml')) {
    & $ossutil cp "$dataDir\$name" "oss://byrdocs-data/$name"
}
```

不要把 Archive 的 `schema/book.yaml` 等原文件直接当作分类目录：三份 YAML 是格式校验规则。本站搜索使用 `metadata.json`。

## 资料和线上读取核对

```powershell
& $ossutil ls 'oss://byrdocs-file/' --recursive | Select-Object -Last 4
& $ossutil ls 'oss://byrdocs-data/' --recursive | Select-Object -Last 8
Invoke-WebRequest 'https://byrdocs.2382300863.workers.dev/data/metadata.json' -Method Head
```

本次已知文件桶目标为 3372 个对象；数据桶目标为四个已发布对象。桶级 `stat` 统计可能有延迟，对象列表更适合查看正在进行的批量上传。完整性还应按 `reports/resource-manifest.csv` 对照每个 key 和大小。访问网页需确认网络能连接 `workers.dev`；无法访问时先区分 DNS/网络超时与 HTTP 404/5xx。

## 恢复到另一台电脑

1. 解压主站和 Archive 源码 ZIP，安装 Node.js/pnpm、Python/PyYAML、ossutil。
2. 配置新的 Cloudflare 账号、D1、Worker Secrets，检查 `wrangler.toml` 的 D1 ID、OSS Endpoint、Region、桶名。
3. 在阿里云创建或连接两个 OSS 桶，给 RAM 用户相应权限；不要从本归档寻找 AccessKey，本归档故意不保存密钥。
4. 从部署电脑取得完整 `resources/` 资料副本并导入文件桶，用 `data/` 中四个现有文件导入数据桶；若站点域名改变，先重新生成数据。
5. 执行 D1 迁移、构建和 Worker 部署，最后分别检查主站、数据 URL 和几种资料的搜索/预览/下载。
