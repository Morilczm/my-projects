# BYR Docs 主站复现过程

参考指南：<https://blog.byrdocs.org/blog/posts/reproduce-byrdocs/post.html>。本次复现以原项目主站为基础，Cloudflare R2 文件存储改用阿里云 OSS；其他子项目不包含在已完成范围内。

## 1. 环境与源码

- Windows PowerShell；Node.js、pnpm；Wrangler 4.125.0；ossutil 2.1.2；Python 3.10 和 PyYAML 6.0.3。
- 本机主站原位置 `E:\byrdocs-main`，Git remote `https://github.com/Morilczm/byrdoc.git`，归档提交 `c90f42d3a2c2a7315bd6cb66aac041b87dac6885`。
- Archive 原位置 `E:\byrdocs-archive`，归档提交 `25df77900b0c46084d7f81cf9e5275a7427042b7`。
- 资源原位置 `E:\byrdocs`；完整副本保存在部署电脑的 `E:\byrdocs-reproduction\resources`，未上传 GitHub。
- 解压 `source/` 里的两个 ZIP 即可查看当时完整的源码和元信息。源码快照采用 `git archive`，因此不含仓库外的本地改动或秘密文件。

## 2. Cloudflare 主站

Wrangler 登录后，创建 D1 数据库 `byrdocs`，把实际数据库 ID 填入主站 `wrangler.toml` 的 `[[d1_databases]]`。本次数据库 ID 见根目录 README。随后在主站目录执行：

```powershell
pnpm install
pnpm exec wrangler d1 migrations apply byrdocs --remote
pnpm run build
pnpm exec wrangler deploy
```

当时远程 D1 的三份迁移均显示成功。`wrangler.toml` 保留了 Durable Objects、Analytics Engine、静态 assets 等原项目绑定；OSS 替代逻辑见 [R2 替换为 OSS](R2替换为OSS.md)。代码发布可通过 Wrangler 手动部署，或把主站源码仓库连接到 Cloudflare Workers 构建；推送主站代码后是否自动生效，以 Cloudflare 构建和部署记录为准。上传本复现文档不会触发主站部署。

## 3. 阿里云 OSS

在阿里云华北 2（北京）创建 `byrdocs-file` 和 `byrdocs-data` 两个桶。RAM 用户取得这两个桶所需的对象读写权限，AccessKey 只保存在本机 ossutil 配置以及 Cloudflare Worker Secrets 中。实际配置：

```toml
[vars]
OSS_ENDPOINT = "https://oss-cn-beijing.aliyuncs.com"
OSS_REGION = "cn-beijing"
OSS_FILE_BUCKET = "byrdocs-file"
OSS_DATA_BUCKET = "byrdocs-data"
```

Worker Secrets 名称：`OSS_ACCESS_KEY_ID`、`OSS_ACCESS_KEY_SECRET`。它们不是公开 `[vars]`，值不在本归档中。

本机曾用 `ossutil` 将 `E:\byrdocs` 的 PDF、ZIP、JPG、WEBP 上传至 `oss://byrdocs-file/` 根目录。若在此归档目录重做：

```powershell
$ossutil = 'E:\oss-tools\ossutil-2.1.2-windows-amd64\ossutil.exe'
& $ossutil cp 'E:\byrdocs-reproduction\resources' 'oss://byrdocs-file/' -r `
  --include '*.pdf' --include '*.zip' --include '*.jpg' --include '*.webp' `
  --ignore-existing --job 4 --no-progress
& $ossutil ls 'oss://byrdocs-file/' --recursive | Select-Object -Last 4
```

`--ignore-existing` 用于重跑时跳过已存在对象。第一次上传的 3 个失败对象是暂时的 DNS 解析失败，逐个重试后成功；原始日志保存在部署电脑 `E:\byrdocs-reproduction\tools`。目标对象数为 3372。`reports/resource-manifest.csv` 可核对文件名和字节数。

## 4. Archive 数据

`tools/build_byrdocs_data.py` 读取 Archive 的 `metadata/*.yml`，改写每条文件 URL 到本站域名，针对本地存在的原件补入 `filesize`，生成 `metadata.json`；同时将 Archive 的三个 `schema/*.yaml` 的 URL 校验模式改成本站域名后输出。**三个 YAML 是元信息格式规则，不是分类数据列表。**

```powershell
python 'E:\byrdocs-reproduction\tools\build_byrdocs_data.py' `
  --archive 'E:\byrdocs-archive' `
  --resources 'E:\byrdocs-reproduction\resources' `
  --output 'E:\byrdocs-reproduction\data\regenerated' `
  --site-url 'https://byrdocs.2382300863.workers.dev'
```

生成后的四份文件分别上传到 `oss://byrdocs-data/metadata.json`、`book.yaml`、`test.yaml`、`doc.yaml`。已上线的文件副本见 `data/byrdocs-data-2026-10-03/`。主站 `/data/*` 路由从 `byrdocs-data` 桶读取这些对象；`/files/*` 从 `byrdocs-file` 读取资料。

## 5. 当前限制

- 110 条元信息对应文件本地缺失，但仍在 `metadata.json` 中，搜索到后可能打不开。32 份本地 PDF 缺元信息，无法通过搜索发现。用户决定暂时不处理。
- Archive 的 GitHub Actions 仍引用 R2 API 和 R2 Secrets；需要额外改造才能自动向 OSS 刷新元信息。
- `sitemap.xml`、Wiki、Publish 和备份桶不在这次四份数据文件上传范围内。
- `workers.dev` 在某些大陆网络无法直连；本机走代理可访问，公开使用还需处理域名和网络可达性。
