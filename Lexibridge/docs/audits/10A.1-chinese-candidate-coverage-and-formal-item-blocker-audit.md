## 3. Current Chinese Candidate Sources

Current mainline has an evidence-constrained Chinese candidate generator. It is not a real provider and it does not translate.

Evidence:

- `backend/services/chinese_term_candidates.py:1` states the module extracts from existing governed records and does not translate or call an LLM.
- `backend/services/chinese_term_candidates.py:311` finds exact English-term matches in existing `ConceptAlignmentCard` rows.
- `backend/services/chinese_term_candidates.py:396` finds exact English-term matches in legacy `Term` and `TerminologyCard` rows.
- `backend/services/chinese_term_candidates.py:444` extracts short Chinese spans around exact English terms in governed bilingual chunks.
- `backend/services/chinese_term_candidates.py:449` supports only a narrow set of explicit patterns: Chinese before English parentheses, English before Chinese parentheses, and alias forms using `又称`, `也称`, `即`, or `称为`.
- `backend/services/chinese_term_candidates.py:617` merges and ranks candidates and marks risks such as `no_chinese_candidate_found`, `ambiguous_chinese_candidates`, and `weak_candidate_score`.

Important boundary: current mainline does not contain the later Task 10.5/10.6 pair-local eligibility pipeline or its real second-course metrics. The current generator can extract explicit bilingual patterns from governed chunks, but it is not the same as a full real-corpus pair funnel.

| Evidence persistence | `backend/services/document_alignment_processing_orchestrator.py:439` | prepared item passes scope validation and lease fencing | item becomes `evidence_ready` |

This directly answers a recurring ambiguity: a Run-level `blocked` status does not necessarily mean every Item failed at the same stage. Current code can persist candidate summaries for evidence-insufficient blocked Items, and root status is recomputed from all Items.

## 9. Main Findings

1. Current mainline cannot substantiate the historical `2/250` second-course coverage claim.
2. Current code has a limited governed Chinese candidate path from existing cards, legacy terminology, and explicit bilingual chunks.
3. Current Formal preparation intentionally disables low-quality and needs-review evidence by default.
4. Current evidence retrieval rejects chunks without `source_uid`; the current DB has no chunks with `source_uid`.
5. Current DB has 40 mixed-script chunks, but no generic explicit pair hints under the audit scanner and no governed evidence identity.
6. Current DB has zero Formal Items, so selected Item matching and blocker proportions cannot be calculated from production data.
7. Existing tests prove the pipeline can succeed in controlled governed fixtures and can block safely when candidates/evidence are missing.
8. There is not enough current-mainline data to decide whether missing Chinese coverage is mainly A, B, or C on real course documents.

## 10. Practical Interpretation

The current mainline is not yet ready for a Provider-first assumption. The observed blocker is earlier and more basic:

- Current production DB lacks a governed Formal Item population to audit.
- Current upload/parser/indexing data in the DB does not expose governed `source_uid`, `chunk_uid`, or locators.
- Current mainline does not include the later real-corpus pair funnel and pair-local eligibility repairs.

Therefore, the responsible next step is not to expand regexes or invoke a real Provider from this branch. It is to restore a real, governed Formal Item sample in mainline or integrate the later candidate/bilingual worktree chain and then re-run this coverage audit against real items.
